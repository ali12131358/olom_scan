Backend و Frontend را در **دو ترمینال جدا** اجرا کنید:

### ۱) Backend (پورت 8001)
```powershell
cd C:\path\to\.olom_net_scan
.\Scripts\activate   # اگر venv دارید
python main.py
```
یا دوبار کلیک روی `start_backend.bat`

یا `start_frontend.bat`

# اسکنر مجاز IPv4 و MikroTik

این پروژه یک کتابخانه پایتون، API مبتنی بر FastAPI و رابط وب React برای ارزیابی شبکه‌های IPv4 با مجوز است. هیچ اسکن خودکاری هنگام اجرا انجام نمی‌شود؛ فقط هدف‌هایی بررسی می‌شوند که کاربر صریحاً وارد کرده است.


## بک‌اند محلی روی کلاینت (Local Agent)

برای اسکن شبکهٔ کلاینت و جلوگیری از قطع شدن API هنگام VPN، بک‌اند باید روی **همان کامپیوتر کاربر** اجرا شود (`http://127.0.0.1:8001`).

1. از رابط وب دکمهٔ **دانلود Local Agent** را بزنید (یا فایل `frontend/public/local-agent.zip`).
2. Extract کنید و `start_backend.bat` (ویندوز) یا `./start_backend.sh` (لینوکس/مک) را اجرا کنید.
3. UI می‌تواند روی سرور باشد؛ مرورگر کلاینت به بک‌اند محلی خودش وصل می‌شود.
4. با وصل VPN، بک‌اند محلی قطع نمی‌شود و اسکن از دید شبکهٔ همان سیستم انجام می‌شود.

## ساختار پروژه

- `scanner_lib/`: پارسر هدف، اسکن موازی، مدل‌ها و گزارش CSV
- `backend/main.py`: API و مدیریت jobهای پس‌زمینه
- `frontend/`: رابط فارسی React/Vite و کنترل محلی backend
- `tests/`: آزمون‌های واحد بدون نیاز به شبکه

## نیازمندی‌ها و نصب

Python 3.10 یا جدیدتر، Node.js 18 یا جدیدتر و npm لازم است. در ریشه پروژه، محیط پایتون را بسازید و وابستگی‌های backend را نصب کنید:

### Windows PowerShell

```powershell
py -3 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -e .
```

### Linux/macOS

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install -e .
```

وابستگی‌های رابط را نیز نصب کنید:

```sh
cd frontend
npm install
cd ..
```

## اجرا و کنترل یک‌کلیکی از رابط

در ریشه پروژه سرور توسعه React/Vite را اجرا کنید:

```sh
cd frontend
npm run dev
```

صفحه را در `http://localhost:5001` باز کنید. هنگام اجرای اسکن، نوار پیشرفت زنده با درصد، شمار هدف‌های تکمیل‌شده و وضعیت اسکن نمایش داده می‌شود؛ در حالت بیکاری این نوار پنهان است. کارت «وضعیت سرور FastAPI» در صفحه اصلی وضعیت API را نمایش می‌دهد و دکمه‌های «شروع سرور» و «توقف سرور» امکان راه‌اندازی و توقف backend را مستقیماً از همان رابط فراهم می‌کنند. با کلیک روی دکمهٔ «شروع سرور» در صفحهٔ اصلی، Vite اجرا می‌کند: `uvicorn backend.main:app --host 0.0.0.0 --port 8001` از ریشهٔ پروژه؛ فرایند به `0.0.0.0` مقید است تا از طریق NAT و شبکهٔ محلی در دسترس باشد (پورت‌های 5001 و 8001). این اجرا در زمان توسعه به‌عنوان فرزند Vite انجام می‌شود و بخشی از build تولیدی نیست. توقف فقط روی فرایندی انجام می‌شود که همین کنترلر راه‌اندازی کرده، نه روی FastAPI خارجی موجود.

کنترلر ابتدا فایل اجرایی `uvicorn` را از محیط پایتونی که با `PYTHON_EXECUTABLE` مشخص شده پیدا می‌کند (در Windows از `Scripts` و در POSIX از `bin`)؛ اگر این متغیر تنظیم نشده باشد، `uvicorn` را از `PATH` می‌گیرد. در صورت نبودن executable، وابستگی‌ها را با `pip install -r requirements.txt` نصب کنید و مطمئن شوید پوشهٔ `Scripts`/`bin` محیط مجازی در `PATH` است یا `PYTHON_EXECUTABLE` را روی مفسر همان محیط تنظیم کنید. نمونه:

```powershell
$env:PYTHON_EXECUTABLE = "C:\path\to\project\.venv\Scripts\python.exe"
```

```sh
PYTHON_EXECUTABLE=/path/to/project/.venv/bin/python npm run dev
```

همچنین می‌توانید backend را دستی و مستقل اجرا کنید (از ریشه پروژه و با محیط پایتون فعال):

```sh
uvicorn backend.main:app --host 0.0.0.0 --port 8001 --host 127.0.0.1
```

سپس در ترمینال دیگری `cd frontend && npm run dev` را اجرا کنید. رابط، backend خارجی فعال را تشخیص می‌دهد؛ دکمه توقف کنترلر آن فرایند را متوقف نمی‌کند.

## پورت‌ها و دسترسی محلی

- Backend FastAPI: پورت **8001**، متصل به `127.0.0.1`؛ مستندات: `http://127.0.0.1:8001/docs`.
- Frontend Vite: پورت **5001** (در صورت اشغال‌بودن پورت، Vite ممکن است پورت جایگزین اعلام کند). تنظیم `host: true` در Vite برای دسترسی به صفحه توسعه از میزبان شبکه فعال است؛ این به معنی بازشدن backend نیست.
- مسیرهای مدیریتی Vite برای start/stop/status فقط درخواست‌های loopback (`127.0.0.1`/`::1`) را می‌پذیرند. خود backend نیز فقط روی loopback گوش می‌دهد. برای استفاده محلی، صفحه را از همان رایانه باز کنید.

برای تغییر پورت backend، مقدار `BACKEND_PORT` در `frontend/vite.config.js` را با پورت اجرای Uvicorn هماهنگ کنید و آدرس API در `frontend/src.jsx`/تنظیمات محیطی را نیز به‌روز کنید. برای تغییر پورت frontend، `server.port` در `frontend/vite.config.js` و originهای مجاز در `backend/main.py` را هماهنگ کنید. نمونه متغیر `VITE_API_BASE_URL` در `frontend/.env.example` است؛ آن را در `frontend/.env` تنظیم کنید تا آدرس API رابط تغییر کند.

## هدف‌های ورودی

هر خط یا خانه CSV می‌تواند یک IPv4، CIDR یا بازه inclusive باشد؛ نمونه: `192.168.1.10`، `10.10.0.0/24`، `192.168.1.20-30` یا `192.168.1.20-192.168.2.5`. هدف‌های تکراری حذف می‌شوند و ورودی نامعتبر یا عبور از سقف تعداد هدف‌ها خطا می‌دهد. در CIDRهای بزرگ‌تر از /31 آدرس شبکه و broadcast کنار گذاشته می‌شوند.

پورت‌های 8291 (Winbox) و 8728 (RouterOS API) همیشه به فهرست پورت‌های انتخابی افزوده می‌شوند. هر probe TCP فقط برای میزبان پاسخ‌دهنده به ping انجام می‌شود. نتیجه پورت‌ها به صورت `open`، `refused`، `timeout` یا `error` گزارش می‌شود. timeout الزاماً به معنی فیلترشدن نیست.

## توقف (لغو) اسکن

هر اسکن به‌صورت مشارکتی قابل توقف است. در رابط وب، هنگام اجرای اسکن دکمهٔ «توقف اسکن» نمایش داده می‌شود؛ کلیک روی آن درخواست لغو را به backend می‌فرستد و وضعیت به «اسکن لغو شد» تغییر می‌کند.

- Endpoint: `POST /scans/{scan_id}/cancel` — برای jobهای در صف یا در حال اجرا، `threading.Event` لغو را تنظیم می‌کند و پاسخ `{"scan_id":…, "status":…, "cancel_requested":true}` برمی‌گرداند. فراخوانی مجدد بی‌خطر است (idempotent) و برای شناسهٔ ناموجود خطای 404 می‌دهد.
- در کتابخانهٔ `scanner_lib.scanner.scan_targets` پارامتر اختیاری `cancel_event` (از نوع `threading.Event`) پذیرفته می‌شود. کارگرها پیش از شروع هر هدف و همچنین بین probeهای پورت، وضعیت این Event را بررسی می‌کنند و در صورت لغو، کار را متوقف می‌کنند.
- پس از لغو، یک `ScanReport` جزئی (partial) همیشه به‌صورت تمیز برگردانده می‌شود: نتایج میزبان‌هایی که تا لحظهٔ لغو کامل شده‌اند حفظ می‌شوند، آیتم‌های هنوز در صف با `cancel_futures` کنسل می‌شوند، و پرچم `canceled` در گزارش `True` است. اگر کارگری به‌طور غیرمنتظره خطا بدهد، خطا شمرده می‌شود اما گزارش جزئی همچنان سالم برمی‌گردد.
- دانلود CSV برای اسکن‌های لغوشده: خروجی‌های جزئیِ اسکن لغوشده قابل دانلود هستند. کافی است پس از تغییر وضعیت به `canceled`، همان مسیرهای همیشگی را صدا بزنید:

```
GET /scans/{scan_id}/reports/ping_responders
GET /scans/{scan_id}/reports/mikrotik_candidates
GET /scans/{scan_id}/reports/potential_non_mikrotik
GET /scans/{scan_id}/reports/winbox_open_api_closed
```

پاسخ HTTP برای اسکن لغوشده همان CSV جزئی با UTF-8 BOM است؛ برای jobهایی که هنوز به `done` یا `canceled` نرسیده‌اند خطای 409 «گزارش هنوز آماده نیست» برگردانده می‌شود. در رابط وب، پس از لغو، لینک‌های دانلود CSV همان‌جا در کارت پیشرفت ظاهر می‌شوند.

## دسته‌بندی گزارش‌ها

- پاسخ‌گو به پینگ: تمام میزبان‌هایی که ping پاسخ داده‌اند.
- نامزد MikroTik: حداقل یکی از پورت‌های 8291 یا 8728 باز است؛ این فقط نشانه اولیه است.
- احتمالاً غیر MikroTik: هیچ‌یک از دو پورت باز نیست؛ این نتیجه قطعی نیست.
- Winbox باز / API بسته: پورت 8291 باز و پورت 8728 صریحاً refused است.

گزارش‌ها CSV با UTF-8 BOM و ستون‌های IP، دسته‌بندی، پورت‌های باز همراه نام سرویس، شماره پورت‌های باز و وضعیت دو پورت اصلی هستند.

## دیتابیس SQLite دستگاه‌ها

هر دستگاهی که در اسکن‌ها پیدا می‌شود (میزبان‌های پاسخ‌دهنده به ping با IP و پورت‌های بازشان) به‌طور خودکار در یک پایگاه‌داده SQLite ذخیره می‌شود:

- فایل دیتابیس: `devices.db` در ریشهٔ پروژه، ساخته‌شده به‌صورت خودکار هنگام اجرای backend (ماژول `backend/db.py`، فقط با `sqlite3` استاندارد پایتون).
- جدول `devices`: `ip` (کلید اصلی)، `ping_ok`، `open_ports`، `port_states`، `classification`، `first_seen`، `last_seen`، `seen_count`.
- بدون رکورد تکراری: هر IP فقط یک ردیف دارد. در اسکن‌های بعدی نتایج جدید با قبلی‌ها ادغام می‌شوند؛ پورت‌های باز به‌صورت اجتماع (union) ترکیب می‌شوند، وضعیت‌های تازه‌تر جایگزین قدیمی می‌شوند و `seen_count` و `last_seen` به‌روزرسانی می‌شوند. دسته‌بندی `mikrotik_candidate` حفظ می‌شود.
- دسترسی‌ها thread-safe هستند (قفل سطح ماژول) تا از workerهای FastAPI امن باشد.

### API گزارش‌گیری از دستگاه‌ها

- `GET /devices` — فهرست دستگاه‌ها با فیلتر و صفحه‌بندی. پارامترها: `classification` (یکی از `mikrotik_candidate`، `non_mikrotik`، `special`)، `has_port` (شماره پورت باز)، `q` (جستجوی زیررشتهٔ IP)، `limit`، `offset`. پاسخ شامل `total` و `devices` است.
- `GET /devices/{ip}` — جزئیات یک دستگاه.
- `GET /devices/export.csv` — خروجی CSV با UTF-8 BOM (ستون‌ها: ip، ping_ok، open_ports، port_8291، port_8728، classification، first_seen، last_seen، seen_count)؛ همان فیلترها پذیرفته می‌شود.

در رابط وب، بخش «گزارش دستگاه‌ها» همین داده‌ها را نمایش می‌دهد و امکان دانلود CSV را فراهم می‌کند. فایل `devices.db` دادهٔ زمان اجراست، در `.gitignore` آمده و در بستهٔ انتشار پروژه قرار نمی‌گیرد.

## امنیت و مجوز

این ابزار را فقط روی میزبان‌ها و شبکه‌هایی اجرا کنید که مجوز روشن برای ارزیابی آن‌ها دارید. محدوده‌های خصوصی یا محلی به‌طور ضمنی اسکن نمی‌شوند. API برای استفاده محلی توسعه تنظیم شده و پیش از انتشار عمومی باید احراز هویت، محدودیت نرخ، پاک‌سازی jobها و سیاست CORS مناسب محیط اضافه شود. jobها در حافظه‌اند و با restart از بین می‌روند.
